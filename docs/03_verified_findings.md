### F8 が発覚するまでの経緯(教訓)

最初に全32個のCCを1マクロに入れて3種類を書き込んだが、3種類とも同じ音になった。32個のうち**先頭10個が3種類で共通の値**(アルペジエーターOFFなど)だったため、10個で打ち切られた結果、3つとも同一内容になっていた。
それまでの「成功した」テストは、どれも判定用のCCを先頭に置いていたので問題が見えなかった。

→ **マクロ用のCCは、音色間で差の大きいものから順に並べる。共通の土台はマクロに入れない。**

### 聴感判定の失敗例(教訓)

容量テストで「細い音(CC#70=16)になれば成功」と判定させたが、埋め草に CC#12=127 / CC#79=0 / CC#75=10 を混ぜていたため、打楽器的な強いアタックになり、ユーザーは「むしろ太くなった」と報告した。記録自体は成功していた。

→ **判定は「鳴る/無音」のような二択にする。** CC#7=0 を使う無音テストが確実だった。

### 無音テストは「片道」(教訓、T5)

T5 では「PC89〜128 を全部無音にして、SELECT+→ で消えた回数 N、← で戻った回数 K を数える」設計にしたが、K は測れなかった。CC#7=0 は**チャンネルの状態**として残り、工場プリセットの PC に移っても音量は戻らない(F18)。
→ **「戻った」を判定に使うなら、戻す側も CC#7=127 を含むマクロにする。** 無音にするのは1枠だけにして、周りを「音量最大マクロ」で囲む(T7)。

### Domino は1トラックに複数チャンネルが混ざった SMF を読めない(T2)

「1トラック内に複数のチャンネルが混合しています。読み込みを中止します。」で中止される。
→ **MIDIファイルは format 1 で、チャンネルごとにトラックを分ける。** 同じ tick に別チャンネルのイベントを置かない(トラック間の順序が保証されないため)。

**U1 は結果が食い違っている。** 無音マクロを置いたPCだけが無音になり、→ が +1 だとすると、
- T7: 9回目の着地 = PC89(K=0)
- T8: 9回目も無音 → 着地 = PC90。k=5 から 8回目の着地 = PC85、9回目 = PC95(= J-POP サビで鳴るはず)
となり、どれも両立しない。考えられる原因(未検証):
- ボタンの押し数が数え間違いになりやすい(押しっぱなしでのキーリピート、チャタリング)
- 電源投入時のPCカウンタの開始値が、毎回同じではない
- コントローラーでのPC変更が、MIDIのPC受信とは違う動きをする
→ **「押した回数」に頼る校正は信頼できない。** 1回の測定で見るのを「9回押した直後に無音か」の1点だけにし、無音マクロを置くPCの範囲を半分ずつ変えて何回か測る方式(二分探索)なら、音量0が残る問題(F18)も押し数の問題も避けられる。優先度はユーザーと相談 → **ユーザー判断: PCの切り替えは PC/MIDIキーボード側で行えばよい。コントローラーの校正はしない。**

### 本ソフト 段階3 の実機確認(途中、2026-09-29、`hw_tests/STAGE3_APP_CHECK.md`)

- A, B(1)(2)(3), C(1) は合格。**アプリからの書き込み(マクロ17=[CC#7=0] → PC97)は実機で効いた**(ログ 23:03:13〜18 の送信は T0 と同じ手順)

- microKEY2 は送信chを変えられないため、D 以降は実施できなかった → スルーの演奏を「開いているタブのch」で鳴らす機能を追加した

**仮説(U14)**: 記録中に送ったCCのうち、**その時点の値と同じもの**は記録されない。T0 でマクロ19を記録したのは電源ON直後で、CC#7・CC#11 はもともと127だった。だとすると、マクロ19は空になる。
これが正しければ、T0 のマクロ11(J-POP標準)の CC#73=0・CC#65=0 も記録されていない(記録した時点で、どちらも既定値の0だった)。
→ **T10 で否定された**(下記 F21)。

**T10 の結果**(マクロ21 = 音量127のまま [CC#7=127] を記録 → PC99、マクロ22 = 音量0にしてから [CC#7=127] を記録 → PC100):
1 何もしない=鳴った / 2 PC97=無音 / 3 PC99=**鳴った** / 4 PC97=無音 / 5 PC100=鳴った。
→ 同じ値のCCも記録される。**では C(2) で PC96 が音量を戻さなかった理由は未解明。** 有力な仮説は次のとおり。

## 実機テストの方法論(このプロジェクトで有効だったもの)

1. **1回のテストで1つのことだけ調べる。** 切り分けは梯子状に(PCが届くか → CCが届くか → マクロ実行 → 記録 → 割り当て)。
2. **判定は二択。** 「鳴る → 操作 → 無音?」の形。
3. **調べたいCCを先頭に置く**(容量10の制約)。
4. 判定用の変化を起こす前に、**わざと逆の状態にしてから**操作する(例: CC#70=80で太くしてからマクロ実行)。
5. テストで無音にしたら、**最後に必ず音量を戻す**。
6. 書き込み後に**電源を入れ直してから**確認する。記録中のCCが生で残っているため、入れ直さないと記録内容と区別できない。
7. 番号のズレが疑われるときは、**前後の番号も一緒に試す**(dbg5 で PC92/93/94 を試したのが有効だった)。
8. 書き込み系のテストは使っていないマクロ番号・PC番号で行い、本番の番号を汚さない。

## MIDIファイル生成の実務メモ

- TPQ=480。テスト用のCC送信間隔は 30〜60tick(100BPMで37.5〜75ms)で問題なかった。
- マクロ記録の手順: `CC49=47 → CC45=n → (CC最大10個) → CC45=0 → 待ち(約1.5秒) → CC47=n → CC51=v → 待ち(約1.7秒)`。待ち時間は余裕を見た値で、下限は未測定。
- Dominoで開くとき「コントロールチェンジマクロを復元しますか?」には「いいえ」。生のCC番号のまま残る。
- Domino の音源設定を GM にしていると、PC番号がGMの音色名で表示されるだけで、送信値は変わらない。
